PRIME-AGENT TOOLING SYSTEM
===========================

Purpose
-------
This is an ASCII architecture map of the TypeScript tooling system and its
connection to the persistent Python/RLM runtime.  It distinguishes:

  * tool definition and registration,
  * tool lookup and execution,
  * the Python kernel process and protocol,
  * RLM host policy and child sessions, and
  * Python-side skills and delegation.

The strongest source for the RLM boundary is:
  packages/coding-agent/docs/rlm.md
  packages/coding-agent/docs/rlm-runtime.md

The module inventory and call paths below were checked against the local
checkout by a static audit on 2026-09-13.  The architecture remains descriptive
documentation, not a substitute for reading the implementation before changing
it.

2. WHERE TOOLS COME FROM
------------------------

There are three principal sources of tool definitions.  They converge before
execution in AgentSession's active tool registry.

Current-checkout detail: `createAllToolDefinitions()` currently returns only the
`ipython` definition.  The tools directory still contains factories and helpers
for bash, edit, ACP/MCP, previews, mutation queues, rendering, and truncation;
those modules are not automatically proof that each tool is active by default.

  BUILT-IN FACTORIES
  ------------------

  +-----------------------------+
  | core/tools/*.ts             |
  | e.g. ipython.ts             |
  |                             |
  | create...ToolDefinition()   |
  +--------------+--------------+
                 |
                 | ToolDefinition
                 v

  SDK CUSTOM TOOLS
  ----------------

  +-----------------------------+
  | AgentSession config         |
  | customTools: [...]          |
  | defineTool(...)             |
  +--------------+--------------+
                 |
                 | ToolDefinition
                 v

  EXTENSION-REGISTERED TOOLS
  --------------------------

  +-----------------------------+
  | extension module             |
  | default factory(api)         |
  +--------------+--------------+
                 |
                 | api.registerTool(definition)
                 v
  +-----------------------------+
  | core/extensions/loader.ts   |
  | ExtensionAPI construction   |
  | discovery + factory loading |
  +--------------+--------------+
                 |
                 v
  +-----------------------------+
  | extension tool map          |
  | ExtensionRunner             |
  | core/extensions/runner.ts   |
  +--------------+--------------+
                 |
                 | RegisteredTool objects
                 v
  +-----------------------------+
  | core/extensions/wrapper.ts  |
  | context-aware adaptation    |
  +--------------+--------------+
                 |
                 | AgentTool objects
                 v

                         +-------------------------------+
                         | AgentSession._refreshToolRegistry |
                         | combines built-ins, customTools, |
                         | and extension tools              |
                         +---------------+----------------+
                                         |
                                         v
                         +-------------------------------+
                         | active tool definitions        |
                         | active AgentTool registry      |
                         +-------------------------------+

Important distinction:

  ToolDefinition = metadata, parameter schema, and execute implementation.
  RegisteredTool = extension-side definition plus registration/source context.
  AgentTool      = executable shape consumed by the agent loop.

The wrapper layer adapts registered definitions to the runtime shape.  It is
not the same responsibility as the kernel manager, which runs Python code.

The kernel is a durable control environment, not a security sandbox.  Python
and shell commands run with the worker's operating-system permissions.


5. RLM DELEGATION INSIDE IPYTHON
--------------------------------

A call to await rlm(...) is nested inside the ipython execution path.  It is
not a second ordinary model-facing AgentTool call and it is not local Python
recursion.

  Parent model
       |
       | ipython code: await rlm("review the API")
       v
  +-----------------------------+
  | ipython AgentTool           |
  +--------------+--------------+
                 |
                 v
  +-----------------------------+
  | Python REPL / rlm package   |
  | callable rlm object         |
  +--------------+--------------+
                 |
                 | host_request event: rlm.run
                 | JSON line over runtime stdio
                 v
  +-----------------------------+
  | ReplKernelManager           |
  | dispatches typed request    |
  +--------------+--------------+
                 |
                 | HostRequestHandlers
                 v
  +-----------------------------+
  | Parent AgentSession         |
  | runRlmChild() / RLM policy  |
  |                              |
  | - check RLM_DEPTH            |
  | - resolve/inherit model      |
  | - validate thinking level    |
  | - admit child                |
  | - update child registry      |
  | - attribute usage           |
  +--------------+--------------+
                 |
                 | immediate host reply
                 v
  +-----------------------------+
  | RLMSpawnHandle              |
  | child id, name, session dir,|
  | model                       |
  +--------------+--------------+
                 |
                 | returned to Python cell
                 v
  +-----------------------------+
  | ipython result to parent    |
  +-----------------------------+

The original call returns admission only.  It does not contain the child's
answer and normally does not wait for child completion.

The parent-scoped child registry is authoritative in TypeScript.  Child
transcripts and artifacts can remain addressable after the interactive client
detaches, subject to the session/daemon mode.


7. HOST-REQUEST CONTROL PLANE
-----------------------------

The data plane executes Python cells.  The control plane asks the TypeScript
host to perform operations whose authoritative state is outside Python.

  Python code / bundled skill
             |
             | await host_request(type, payload)
             v
  +-----------------------------+
  | runtime host_request event  |
  +--------------+--------------+
                 |
                 | JSON-lines stdio
                 v
  +-----------------------------+
  | ReplKernelManager           |
  | typed dispatch table        |
  +--------------+--------------+
                 |
                 v
  +-----------------------------+
  | AgentSession host handlers  |
  +--------------+--------------+
                 |
        +--------+--------+------------------+------------------+
        |                 |                  |                  |
        v                 v                  v                  v
  rlm.run          goal.*            agent_message.*       heartbeat/*
  child policy     goal state        daemon messaging      scheduling

The same pattern applies to bundled Python skills such as goal, agent_message,
rlm_heartbeat, and compact.  The skill is a Python client; TypeScript remains
the authority for credentials, provider execution, transcript writes, child
routing, scheduling, and lifecycle state.

9. WHAT IS AND IS NOT A TOOL
----------------------------

  IS AN AgentTool / tool-system object:

    * a ToolDefinition produced by a built-in factory;
    * an SDK customTool / defineTool definition;
    * an extension tool registered through ExtensionAPI.registerTool;
    * a wrapped AgentTool in AgentSession's active registry;
    * the ipython boundary exposed to the parent model.

  IS NOT necessarily a separate AgentTool:

    * Python's bash() helper;
    * a Python-backed skill callable;
    * rlm(...), which is a Python API backed by host_request;
    * goal/agent_message/heartbeat/compact Python clients;
    * a child AgentSession (it is a session, not a tool).

Extensions may intentionally add more AgentTools.  The RLM design does not
require one model-facing AgentTool for every capability.


10. LIFECYCLE AND STATE
-----------------------

  first ipython use
        |
        v
  kernel Python environment is resolved/bootstrapped
        |
        v
  python -m rlm.repl starts
        |
        v
  namespace remains persistent across ordinary calls
        |
        +--> interrupt / shutdown through ReplKernelManager
        |
        +--> snapshot / restore for persisted sessions (where enabled)
        |
        +--> child sessions and host-owned registries remain in TypeScript

Relevant persisted concepts include:

  * kernel namespace snapshots;
  * root and child session artifacts;
  * harness state;
  * scheduled jobs;
  * child registry and usage attribution.

Persistence connects the Python control environment to the normal session
lifecycle.  It does not move provider credentials or authoritative child policy
into Python.

12. IMPORTANT SOURCE-VERIFICATION NOTES
---------------------------------------

  + DeepWiki has been useful for candidate paths and symbols, but it has also
    conflated wrapper modules and speculated about files.  The local audit
    confirmed the two wrapper modules are separate:

      core/tools/tool-definition-wrapper.ts
      core/extensions/wrapper.ts

  + The RLM documents and local source specify newline-delimited JSON over
    stdio and `python -m rlm.repl`.  A claimed ZMQ `execute_request` path is
    rejected: local source/dependencies contain no ZMQ, Jupyter, IPython
    kernel, or KernelGateway implementation for this path.

  + The local checkout does contain `bash.ts`, `edit.ts`, `bootstrap.ts`, and
    `state-snapshot.ts`.  Their existence is now verified, but presence alone
    does not mean every factory is active in `createAllToolDefinitions()`.

  + Keep these boundaries separate when reasoning about changes:

      definition != registration != wrapping != kernel execution
      kernel execution != RLM host policy
      child admission != child completion
      Python capability != AgentTool registration
      tool availability != tool-module existence
